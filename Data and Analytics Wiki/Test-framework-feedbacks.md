# Testing Team Structure
1. Test Manager/s
2. Test Analyst/s
3. Non-testers

Test Manager
------------

Leads testing for Emerge and manages testing resources. Reports to the CIO, who owns the framework. Responsible for putting the framework into practice using the Test Framework documentation, even though it is not yet fully clear about the how-to.

Test Analyst
------------

Runs tests on different projects and keeps the test repository up to date. Trains non-testers to run tests. Creates and prepares test cases so both test analysts and non-testers can use them.

Non-Testers
-----------

Includes different UAT teams or project teams without professional testers but with support from an assigned tester. Work with testers to report bugs and are able to run tests like analysts.


(At this stage, the test framework needs more detailed guidance on **how to apply it**.)

Test Policies
-------------

We need to define a clear testing policy for Emerge and ensure vendors follow it. This policy should also be part of the requirements when signing up new vendors. But how do we actually apply it according to the framework?

Test Risk Levels
----------------

To start, use two levels:
*   **Critical**: Bugs that must be fixed immediately because they break daily functions of the software or data warehouse.
    
*   **Non-critical**: Bugs that can wait and be investigated later.
    
As testing skills improve, use the Risk-based Testing Decision Matrix to decide bug priorities. This requires clear instructions, and the author of the Test Framework can provide guidance on applying the matrix to Emerge projects.
